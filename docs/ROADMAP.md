# نقشهٔ راه

Roadmap بر اساس gate پیش می‌رود، نه تاریخ حدسی. عبور از هر فاز نیازمند تحقق معیار خروج آن است.

## بازتنظیم خط مبنا، مدیریت ادمین و ساخت رسانهٔ پایه — تکمیل‌شده / گام بعدی: پیکربندی رسانه و درخواست دسترسی منابع

- بازتاب نقش‌های سوپر ادمین و ادمین (سردبیر) در اسناد و راهنماها
- ثبت فاصلهٔ قابلیت‌های موجود با ساخت ادمین، درخواست/اعطای دسترسی منبع، نگاشت دسته‌بندی و ساخت چند رسانه
- حذف داده‌های Mock از runtime داشبورد؛ نگه‌داشتن fixtureهای آزمون
- پاک‌سازی دیتابیس محلی فعال از داده‌های رسانه/منبع/کراول/خبر و حفظ فقط حساب سوپر ادمین
- جایگزینی demo seed با bootstrap محدود اولین سوپر ادمین
- حفظ معماری Front مستقل و Backend مستقل
- ساخت رسانهٔ پایه توسط ادمین با نام و لوگو؛ ایجاد عضویت owner و فعال‌کردن همان رسانه

خروج: خط مبنای محلی فقط سوپر ادمین دارد، هیچ Media/Source/Crawl/Article نمونه‌ای فعال نیست، demo seed قابل اجرای مجدد نیست، و gap list برای شروع vertical slice ثبت شده است.

گام بعدی: ادامهٔ wizard رسانه برای درخواست منبع/دسته‌بندی، دیدگاه تحریریه و سکوها؛ سپس تصمیم دسترسی سوپر ادمین و نگاشت دسته‌بندی خام منبع.

## فاز ۰ — کشف و جهت طراحی (تکمیل‌شده)

- بررسی سه مخزن مرجع
- تعریف دامنه، معماری و الزامات امنیتی
- Design Brief داشبورد
- ساخت نمونهٔ داشبورد با دادهٔ Mock قراردادی

خروج: تأیید صریح مالک محصول روی جهت UI/UX داشبورد.

## فاز ۱ — پایهٔ محصول (تکمیل‌شده)

- monorepo و Design System تثبیت‌شده
- هستهٔ Media، User، Membership و permission preset
- navigation و shell اصلی داشبورد
- قرارداد job/progress/error
- Audit Log پایه
- جداسازی `front` مبتنی بر Next.js از `back` مبتنی بر Node.js

خروج: کاربر مجاز می‌تواند وارد یک رسانه شود و shell واقعی را ببیند.

## فاز ۲ — دریافت و کراولر (فعال)

- انتقال منطق لازم CrawlerGenerator به ماژول داخلی Backend؛ بدون dependency runtime به مخزن مرجع
- Source Catalog سراسری، Media Source Subscription، نسخهٔ crawler، اجرا، health و schedule
- ورود Platform Raw Article، fan-out به Media Inbox، deduplication و quarantine ورودی مشکوک
- worker مستقل و آمادهٔ توزیع افقی
- UI صف ورودی و خطاها

خروج: یک crawl سراسری خبر واقعی را وارد Inbox تمام Mediaهای subscriber می‌کند و مسیر آن قابل ردیابی است.

## فاز ۳ — تحریریه (تکمیل‌شده)

- انتقال منطق و promptهای لازم sardabir به ماژول Editorial در Backend
- Editorial Policy نسخه‌دار
- Story، Article Version و Approval
- صف دستی/خودکار صفحه‌بندی‌شده، مقایسهٔ خطی/کنارهم و تأیید انسانی نسخهٔ دقیق
- سرویس/زیرسرویس، بخش اصلی/ثانویه، اتصال/قطع منابع با provenance تاریخی
- تولید، ویرایش و پیش‌نمایش renditionهای Social/WebCard/WebFull

خروج: خبر خام به نسخهٔ تأییدشدهٔ قابل انتشار تبدیل می‌شود. این gate با آزمون integration نسخه/تأیید، ۴۳ تست Backend، ۲ تست diff، build مستقل و بازبینی رابط در 2026-10-07 بسته شد؛ انتشار واقعی متعلق به فازهای بعدی است.

## فاز ۴ — سایت و انتشار وب (تکمیل‌شده)

- انتقال منطق لازم News-website-builder به ماژول Site Builder و lifecycle سایت
- قرارداد تحویل محتوا به سایت ساخته‌شده
- preview، schedule، publication result و retry

خروج: یک خبر تأییدشده بدون انتشار تکراری روی سایت مقصد قرار می‌گیرد. این gate در 2026-10-14 با Site Builder داخلی، snapshot دقیق WebCard/WebFull، سایت عمومی، preview، صف/زمان‌بندی/تغییر زمان/retry، ۵۵ آزمون Backend و ۷ آزمون Front و بازبینی مرورگری مستقل بسته شد. اتصال دامنه و تولید کد دلخواه سایت جدا از این gate هستند (ADR-0020).

## فاز ۵ — بات‌ها و انتشار اجتماعی

- vault/secrets برای credentialها
- حداقل یک adapter شبکهٔ اجتماعی
- Destination، rendition، پیش‌نمایش و صف انتشار
- rate limit، retry و توقف اضطراری

خروج: یک خبر با قالب متناسب روی سایت و حداقل یک کانال منتشر می‌شود.

## فاز ۶ — سخت‌سازی و عرضه

- threat-model review و abuse cases
- تست‌های authorization و tenant isolation
- SAST/dependency/secret scanning
- تست نفوذ API و workerها
- backup/restore، observability و runbook رخداد

خروج: معیارهای امنیت، بازیابی و عملیات production پاس شده‌اند.
