# ADR-0038 — دیباگ مبتنی بر خطا و شروع دریافت پس از اصلاح

تاریخ: ۱۴۰۵/۰۸/۱۲ (2026-11-03) · وضعیت: پذیرفته‌شده

## تصمیم

به درخواست مالک محصول، دکمهٔ «دیباگ کراولر» فرمان اصلاح و بازگشت به دریافت است. پس از قبولی gate کامل دیباگ، نسخه جایگزین و Source فعال می‌شود؛ حتی اگر پیش از درخواست دیباگ متوقف بوده باشد. در همان تراکنش یک run دریافت واقعی با نسخهٔ اصلاح‌شده و correlation مستقل ثبت می‌شود تا منتظر بازهٔ بعدی schedule نماند. این بخش جایگزین قاعدهٔ حفظ توقف پس از دیباگ در ADR-0011 است.

دیباگ همچنان الگوی نسخهٔ فعال، نشانی/کد/مدت خطاهای همان نسخه و نشانی‌های موفق معتبر را بررسی می‌کند. کد خلاصهٔ خطای Source نیز پس از اعتبارسنجی، بدون پیام خام لاگ، به context افزوده می‌شود. صفحهٔ خطادار از مجموعهٔ آزمون حذف نمی‌شود و gate استخراج/دسته‌بندی/حفظ پوشش تضعیف نمی‌شود. نمونه‌های آزمون وارد Inbox نمی‌شوند؛ run بعدی مسیر عادی ingestion و deduplication را طی می‌کند.

شکست دیباگ نسخهٔ فعال قبلی را نگه می‌دارد و دریافت فوری تازه‌ای ایجاد نمی‌کند. توقف کاربر حین دیباگ مقدم است: لغو اجرا با قفل Source با تراکنش فعال‌سازی و ساخت run بعدی هماهنگ می‌شود؛ پاسخ دیررس اجازهٔ فعال‌سازی یا شروع دریافت ندارد.

رابط اثر دکمه را روشن بیان می‌کند. شمار «نیازمند رسیدگی» هم `failed` و هم `degraded` را شامل می‌شود؛ `PARTIAL_EXTRACTION` به معنی استخراج بخشی از خبرهاست و نباید با توقف کامل اشتباه شود.

## اعتبارسنجی

تست Platform API رسیدن کد خلاصه و نشانی خطادار به builder، عدم ساخت run بعد از دیباگ ناموفق، فعال‌شدن Source قبلاً متوقف، یک run فوری با نسخهٔ فعال و لغو حین دیباگ بدون احیای دیررس را بررسی می‌کند. آزمون‌های قبلی حفظ نسخهٔ قبلی و عدم ingestion نمونه‌های تست پابرجا هستند.
