# ADR-0011 — ساخت و فعال‌سازی نسخهٔ آزموده‌شدهٔ کراولر

وضعیت: پذیرفته‌شده — 2026-10-06

## مسئله

ثبت Source قبلاً یک نسخهٔ استخراج عمومی را فوراً فعال می‌کرد؛ ساختار سایت و کیفیت خروجی پیش از توزیع آزموده نمی‌شد. اصلاح یک سایت، تضمین کیفیت سایت جدید نبود.

## تصمیم

- ساخت منبع، Source غیرفعال با وضعیت `building`، نسخهٔ `draft` و Crawl Run با trigger برابر `build` را در یک transaction ایجاد می‌کند. API پاسخ 202 و شناسه‌های source/run دارد.
- Worker HTML صفحهٔ اصلی و نمونه‌های خبر را با URL guard محصول دریافت می‌کند. Codex SDK بومی فقط recipe اعلانی CSS با schema سخت‌گیرانه تولید می‌کند؛ کد تولیدشده اجرا نمی‌شود.
- مدل در پوشهٔ تحلیل جدا، sandbox فقط خواندنی، shell/app/MCP غیرفعال، جست‌وجو و شبکهٔ ابزار غیرفعال و محیط پالایش‌شده اجرا می‌شود. credential سرویس/دیتابیس به process مدل داده نمی‌شود. اطلاعات صفحه ورودی نامطمئن است؛ script/form/header/navigation و query لینک‌ها از evidence حذف می‌شوند. دریافت وب فقط در Backend با SSRF guard انجام می‌شود.
- برای HTML، حداکثر شش نمونه از نقاط مختلف فهرست انتخاب می‌شود؛ فعال‌سازی حداقل سه نمونهٔ معتبر و موفقیت همهٔ نمونه‌های انتخاب‌شده را لازم دارد. عنوان اختصاصی، وجود ظرف متن، متن حداقل ۸۰ نویسه و HTML محتوا بررسی می‌شوند. نمونه‌های خارج از سه صفحهٔ اولیه، پوشش آزمون را افزایش می‌دهند. صفحهٔ متنی و caption تصویری می‌توانند selectorهای متفاوت داشته باشند.
- شکست آزمون با HTML نمونه و feedback پالایش‌شده به مدل برمی‌گردد؛ حداکثر سه تلاش ساخت و سقف ۱۸۰ ثانیه برای هر درخواست مدل وجود دارد. دریافت‌های موقت یک retry دارند. RSS با parser واقعی و وجود item معتبر آزموده می‌شود و نیاز به مدل ندارد.
- آزمون build هیچ Raw Article یا Inbox Item نمی‌سازد. فقط پس از قبولی، run و نسخه و فعال‌شدن Source اتمیک ثبت می‌شوند؛ لغو یا archive جلوی activation را می‌گیرد. API resume نسخهٔ آخر غیر فعال/ردشده را فعال نمی‌کند.
- ساخت مجدد نسخهٔ جدید می‌سازد، ساخت هم‌زمان همان منبع را تکرار نمی‌کند، و پس از قبولی نسخهٔ فعال قبلی را `retired` می‌کند. نسخه‌های تاریخی و Raw Articleهای immutable بازنویسی نمی‌شوند.
- اجرای عادی از recipe و نسخهٔ pinned در run استفاده می‌کند. نسخه‌های عمومی قدیمی تا بازسازی باقی می‌مانند و UI آن‌ها را «آزمون ساخت ثبت نشده» معرفی می‌کند.
- گزارش آزمون در config نسخه ذخیره و در کاتالوگ ادمین نمایش داده می‌شود؛ مراحل تحلیل/تولید/آزمون/اصلاح/فعال‌سازی در log اجرا ثبت می‌شوند.
- نشانگر SDK پس از پاسخ recipe معتبر، برای پنج دقیقه تأیید پاسخ‌دهی مدل را گزارش می‌کند؛ poll هدر درخواست مدل ایجاد نمی‌کند.

## مرز اعتبار

### دسته‌بندی صفحهٔ داخلی

خروجی‌های جدید مدل فیلد الزامی `categorySelectors` دارند؛ برای نسخهٔ ذخیره‌شدهٔ قدیمی نبود این فیلد مجاز است. مدل باید برچسب دسته‌بندی، متاتگ section یا breadcrumb همان صفحهٔ داخلی خبر را بررسی کند و selector خاص بدهد؛ منوی عمومی، keyword، لینک خبر مرتبط و حدس از عنوان جای دسته‌بندی منبع نیستند. شاهد محدود و پالایش‌شدهٔ category/breadcrumb پیش از حذف navigation به مدل داده می‌شود؛ ابزار یا دستور داخل آن اجرا نمی‌شود.

پیش از قبولی، حداقل سه صفحهٔ داخلی باید واقعاً در evidence مدل حضور داشته باشند؛ کشف لینک با حدس اولیهٔ الگو جای تحلیل این صفحه‌ها را نمی‌گیرد. گزارش هر نمونه categories و categoryStatus دارد. الگوی دارای selector دسته‌بندی که هیچ دسته‌بندی استخراج نکند، با `SAMPLE_CATEGORY_MISSING` مردود می‌شود و feedback به دور اصلاح می‌رود. fallback ساختاریافته/metadata/breadcrumb همچنان فعال است. نبود شواهد دسته‌بندی با `not_exposed` هشدار داده می‌شود؛ عنوان و متن معتبر در سایتی که دسته‌بندی منتشر نمی‌کند بی‌جهت مردود نمی‌شوند. گزارش RSS نیز دسته‌بندی feed را نمایش می‌دهد.

### سربرگ محتوای خبر

`header` داخل `main`، `article` یا landmark با `role=main` می‌تواند عنوان، متن اصلی و برچسب دسته‌بندی خبر باشد؛ نمونهٔ واقعی پوشش زندهٔ الجزیره این ساختار را دارد. چنین سربرگی از evidence حذف نمی‌شود و مانع انتخاب ظرف متن یا برچسب دسته‌بندی نیست. سربرگ عمومی سایت خارج از این محدوده همچنان حذف/رد می‌شود؛ navigation، aside، footer و محتوای فعال همچنان حذف می‌شوند.

### دیباگ نسخهٔ ساخته‌شده

دکمهٔ دیباگ یک run مستقل با trigger `debug` و نسخهٔ draft جدید می‌سازد. Codex snapshot الگوی قبلی و کد خطا/آدرس بدون credential و query/مدت خطاهای اخیر همان Source را دریافت می‌کند؛ پیام خام لاگ ارسال نمی‌شود. از خطاهای نسخهٔ مبنای دیباگ، تا ۳۰ جفت یکتای آدرس/کد خطا با گروه‌بندی دیتابیس انتخاب می‌شوند؛ تکرار یک خطا جای سایر خطاها را نمی‌گیرد و خطاهای نسخه‌های کنارگذاشته‌شده وارد این context نمی‌شوند. تمام آدرس‌های خطادار همان origin، مستقل از مسیرهای الگوی جدید، در آزمون اجباری قرار می‌گیرند؛ taxonomy دوباره به‌عنوان خبر آزموده نمی‌شود. دیباگ تمام لینک‌های کشف‌شدهٔ الگوی جدید و قبلی را در محدودهٔ سقف ۵۰۰ لینک هر discovery، بدون ingestion، بازآزمایی می‌کند. حذف لینک سالم الگوی قبلی از discovery جدید با SAMPLE_DISCOVERY_REGRESSION مردود است. نمونه‌های مردود در evidence دور بعد اولویت دارند؛ تعداد تطبیق selectorها، طول متن قبل از حذف، نتیجهٔ استخراج واقعی و طول متن ساختاریافته به مدل داده می‌شوند. خطای دسترسی لینک اجباری هم مانع قبولی است و رفع مشکل selector محسوب نمی‌شود. سقف شش نمونه همچنان فقط برای build معمولی است؛ قبولی دیباگ به موفقیت تمام مجموعهٔ اجباری نیاز دارد و در سایت بزرگ دریافت بیشتری انجام می‌دهد. پس از قبولی، نسخه جایگزین می‌شود و audit اختصاصی دارد؛ شکست، نسخه و وضعیت عملیاتی قبلی را حفظ می‌کند. Source متوقف پس از دیباگ خودکار فعال نمی‌شود. RSS recipe مدل ندارد و دیباگ SDK برای آن در UI غیرفعال است؛ بازآزمایی با parser در مسیر build انجام می‌شود.

قبولی نمونه‌ها تضمین همهٔ صفحه‌های آینده نیست؛ تغییر قالب سایت یا شکست شبکه در اجرا همچنان با partial failure گزارش می‌شود. سایت بدون HTML قابل استخراج، نیازمند JavaScript یا دارای مانع دسترسی با این runtime فعال نمی‌شود. اجرای مرورگر هنوز بخشی از runtime نیست؛ Source ناموفق باید علت و گزارش آزمون داشته باشد.
