# ADR-0036 — همگام‌سازی دسترسی پس از بازیابی کراولر

تاریخ: ۱۴۰۵/۰۸/۱۲ (2026-11-03)

وضعیت: پذیرفته‌شده

## مسئله

شکست ساخت، درخواست تأییدشدهٔ منبع را `crawler_failed` می‌کرد؛ موفقیت بعدی ساخت/دیباگ فقط `crawler_queued` را به دسترسی تبدیل می‌کرد. بنابراین پس از اصلاح موفق YJC، ادمین همچنان پیام شکست و نبود دسترسی می‌دید.

## تصمیم

- فعال‌سازی نسخهٔ موفق و تکمیل درخواست‌های `crawler_queued` و `crawler_failed` در یک تراکنش انجام می‌شوند. داشتن تصمیم ثبت‌شده و رسانهٔ تأییدشده الزامی است.
- ترمیم درخواست ناموفق، اشتراک غیرفعال را روشن نمی‌کند و دامنهٔ اشتراک موجود را بازنویسی نمی‌کند. درخواست pending، ردشده، withdrawn و افزایش دسته با این مسیر تأیید نمی‌شوند.
- برای داده‌های قبلی، راه‌اندازی API از اتصال مالک دیتابیس، درخواست‌های ناموفق را تنها با شاهد اجرای موفق build/debug نسخهٔ فعال ترمیم می‌کند. منبع باید بایگانی‌نشده و قابل دریافت رسانه‌ها باشد. این مسیر تکرارپذیر و دارای audit است؛ GETها داده را تغییر نمی‌دهند.
- قفل رسانه‌های مرتبط پیش از قفل منبع گرفته می‌شود تا با بررسی درخواست و حذف منبع هماهنگ باشد. درخواست و اشتراک نیز پیش از اعمال تغییر بازخوانی و قفل می‌شوند.
- وضعیت توقف کراولر حفظ می‌شود. خبرهای قبلاً دریافت‌شده بدون تکرار به Inbox رسانهٔ مجاز متصل می‌شوند؛ نمونهٔ اعتبارسنجی خبر runtime نیست.

## اعتبارسنجی

تست یکپارچه شکست اولیه و موفقیت build/debug، تکمیل درخواست queued، ترمیم تاریخی روی منبع متوقف، تکرارپذیری، حفظ دسته‌های اشتراک موجود و عدم احیای مجوز غیرفعال را پوشش می‌دهد. موارد بدون تصمیم، رسانهٔ تأییدنشدۀ دیگر، درخواست رد/withdrawn/افزایش دسته، منبع بایگانی‌شده و دریافت مسدود نیز بررسی می‌شوند. API overview وضعیت دسترسی جدید را نشان می‌دهد.
